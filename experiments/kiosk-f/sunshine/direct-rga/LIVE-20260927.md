## Helper acceptance

The actual direct-rga.cpp helper was compiled natively with GCC C++17,
-Wall -Wextra -Werror, then executed inside the installed runtime with device
access. Corrected kernel CSC was enabled temporarily with an independent
restoration timer, and restored to N afterwards.

Eight cases pass: 1920x1080 and 1080x1920, BT601 and BT709, limited and full
range. Each case changes source color bars three times, verifies an asymmetric
top marker and an opaque cursor, rejects an unsupported input format and then
successfully reuses the converter. Maximum color error is one 8-bit value.
See helper-results-20260927.txt.

These are generated linear DMA-BUF sources. They do not establish successful
capture of the actual KMS/AFBC source or end-to-end Moonlight performance.

## Build integration and remaining scope

The optional implementation is included by experiments/kiosk-f/ci/build-runtime.sh
and its matching runtime Containerfile. Default remains OFF; the runtime manifest
records availability separately from activation. No main/release workflow change,
no new full image build, and no push are part of this change.

Activation currently uses SUNSHINE_VYARM_DIRECT_RGA=1 for the Sunshine process
plus the already documented corrected-CSC prerequisite. A dedicated native VyOS
CLI selector is not introduced here. Before default enablement or main release:
qualify mouse/rotation, sustained moving content, audio regression, alternate
kernels/boards and multi-client behavior. This short successful test is for the
current Panthor test kernel and installed Mesa runtime, not every GPU stack.

An initial attempted mouse test still inherited those settings and was stopped;
it is not evidence about mouse operation. The next two 75-second runs explicitly
overrode mouse=enabled and keyboard=enabled on Sunshine's command line without

A follow-up H.264 test explicitly used --absolute-mouse (desktop mode) instead
of relative mode. Absolute mouse packets were received. Rendering was 59.95 FPS

Further user feedback: desktop mode restored the pointer outside Moonlight, but

## Comparison with previously working input configuration

The user confirmed physical touchscreen operation while remote pointer control
failed. ACCEPTANCE-FOLLOWUP-20260927.md (Wayland remote-input investigation)
records the earlier successful input experiment: temporary device-cgroup
permission, ownership-checked uinput evdev nodes inside the kiosk, and selective
udev event forwarding into its network namespace. It explicitly states that this
was not yet an installed service or released CLI implementation.

Current podman inspect of kiosk has only /dev/input/event0 and event1 (physical
input), no DeviceCgroupRules, and only the /run/udev database mount. The direct
Sunshine measurement harness creates its devices in a separate host-network
container and does not perform that earlier bridge. Packet receipt at Sunshine
therefore did not establish delivery to Weston. A client cursor toggle cannot
repair this missing input path. No full /dev/input mount or global privilege
change was made in response.

Next correction must restore the bounded ownership-checked bridge, then make it
lifecycle-aware for CLI control mode: admit only this Sunshine process's virtual
keyboard/relative/absolute pointer nodes, provide necessary read/write access,
forward only their device notifications, and remove stale nodes on process or
container replacement. Keep local touch and view-only policy intact. Re-run the
mouse acceptance only after Weston confirms those devices were registered.

The extra remote-control permission dialog reported by the user has not been
positively attributed. The attempted local XTest cursor shortcut is a possible
client-side trigger; merely submitting the shortcut did not prove its effect.
