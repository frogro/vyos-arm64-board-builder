# VP9/AV1 next-path audit, 2026-09-21

Read-only live kernel audit; no codec driver, DT or production change.
Current ROCK test3 exposes only S264/S265 on rkvdec /dev/video2. Chromium153
selects software VpxVideoDecoder/Dav1dVideoDecoder for VP9/AV1 (prior probes).

## AV1: prioritize direct Hantro/V4L2

- Live CONFIG_VIDEO_HANTRO is not set. The enabled-by-default live DT node
  /video-codec@fdc70000 has compatible rockchip,rk3588-av1-vpu but no driver
  bound. This is a concrete missing prerequisite, not proof of browser failure.
- Linux v6.18 already contains rockchip_vpu981 AV1 operations in
  drivers/media/platform/verisilicon/rockchip_vpu_hw.c. Our local kernel source
  contains the Hantro Kconfig options. Candidate config VIDEO_HANTRO=m and
  VIDEO_HANTRO_ROCKCHIP=y must be built against the exact kernel and dependencies.
- Live node has no iommus property. CmaTotal/CmaFree are 0 kB. Check the actual
  DMA allocation path before load/performance tests: zero CMA alone does not
  prove small allocations impossible, but large contiguous allocations are risky.
- Newer downstream RK3588 work uses the Verisilicon IOMMU (CONFIG_VSI_IOMMU)
  plus a matching DT link. That driver is absent from our checked v6.18 source.
  A backport is a separate kernel task; alternatively investigate a bounded CMA
  reservation with boot fallback. Do not copy a newer board's entire DT/kernel.
- After kernel exposure: enumerate AV1F, run GStreamer/reference pixel comparison,
  map the matching video/media nodes into an isolated Chromium container, then
  prove V4L2VideoDecoder and image correctness. Existing Chromium153 source lists
  AV1_FRAME/VP9_FRAME; this is not proof that the runtime selects the new device.
- A 2024 Chromium-dev report needed Linux AV1 enablement and multi-device
  enumeration patches for Chromium123. Audit current153 before reusing old patches.

## VP9: VDPU381 backend, with conformance caveats

Candidate dongioia/rock5bplus-rkvdec2 pinned tree
2c67fd3a3fde501d3f90082ad7f1c849d4f2d6cc contains
patches/vpu/vp9-vdpu381-adapted.patch and VP9 backend sources. This targets a newer
refactored rkvdec layout, not a proven clean application to our kernel. The author
reports 224/305 fluster results, so this is not universal codec conformance.
Review segmentation/altref and portrait stride corrections, then test Profile0
8-bit first. Profile2/NV15 adds the separate browser-import requirement currently
being built on the NUC. Our present H264/HEVC driver is not evidence for VP9.

## Alternative VA-API/MPP bridge: AV1 documentation discrepancy

woodyst/rockchip-vaapi pinned e8c64ddc528c9b00b8f5c4041d0f28acfab5559d
README lists AV1, but src/rockchip_drv_video.c rk_QueryConfigProfiles explicitly
DOES NOT advertise AV1: comment explains missing OBU reconstruction from VA-API
tile data. It advertises VP9 Profile0/2. Do not present this as working AV1.
Requires matching MPP decode kernel ABI; our MPP encoder success does not prove
that ABI for all decoders. Lower priority than extending existing V4L2 path.
ffmpeg-rockchip independently lists vp9_rkmpp/av1_rkmpp, but its player support
is not an automatic Chromium integration.

## User-supplied Jellyfin reference and agreed priority

https://jellyfin.org/docs/general/post-install/transcoding/hardware-acceleration/rockchip/
inspected2026-09-21. Confirms RK3588 AV1 8/10-bit decoding and H264/HEVC encoding;
the quoted1080p480/4K120 figures describe encoding/transcoding capacity, not
Chromium display throughput. Tutorial uses RKMPP+RGA and Rockchip BSP5.10/6.1,
so it is an alternative stack/reference, not a drop-in validation of test3 V4L2.
The page does not itself establish the exact VC9000D IP naming supplied by user.
For implementation use the checked kernel identifiers rk3588-av1-vpu / vpu981.
AV1 and VDPU381 VP9 are separate decoder paths; do not infer support in one from
the other. User agrees to try the proposed direct Hantro/V4L2 path first.
Order: exact-kernel Hantro/module and DMA prerequisites; isolated AV1 pixel
comparison; Chromium multi-device access and actual hardware playback; performance
and regression tests. VP9 VDPU381 patch review follows separately. Keep BSP/MPP
as a fallback investigation; do not replace production kernel or browser by
copying the Jellyfin setup commands. No new driver built or loaded by this note.
