# Next checks: VP9 Profile2 and H264 reference lists

Research/source audit 2026-09-22. No new live decode tests in this audit.

## VP9 Profile2/10-bit

Current external vp9-live-test3 source ALREADY advertises profiles0/2,
NV12/NV15 and uses capture bytesperline for MV/reference/output addressing.
rkvdec_vp9_validate_frame rejects profiles1/3 and depths other than8/10.
Do not blindly apply an older Profile2 or stride patch on top.
Only Profile0/8-bit has been validated locally so far.

Upstream reports to retain as comparison, not local proof:
https://github.com/beryllium-org/linux-beryllium/pull/8
https://github.com/dongioia/rock5bplus-rkvdec2
These discuss profile2 stride regressions, portrait clips and invalid12-bit
input. Our source has the corresponding mechanisms, but needs runtime tests.

Next: native NV15 decode/hash comparison against packed software reference,
first fixed1080p landscape, then portrait/nonaligned width with a stride-aware
packing/checking helper. Reuse hevc-main10 packing methodology; do not compare
converted10-bit samples as if rounding were decoder corruption. Test8-bit
regressions and clean rejection of unsupported12-bit separately. After the
NV15-capable Chromium build, actual import/render/playback tests for both VP9
Profile2 and HEVC Main10, including seek/restart and format changes. HDR and
color management are separate from10-bit decode.

## New concrete H264 candidate

https://patchew.org/linux/20260901022310.12184-1-vulab@iscas.ac.cn/
2026-09-01 patch v3 by Haotian Zhang, reviewed by Nicolas Dufresne:
media: v4l2-h264: Fix memcmp() size in B1 reference list comparison.
The comparison needs entry size times entry count; the old code compares only
entry-count bytes and can incorrectly swap the first two B1 references.

Verified in BOTH test3 source and the existing test4 source snapshot:
drivers/media/v4l2-core/v4l2-h264.c:443 still uses builder->num_valid alone.
Verified VDPU381 rkvdec-vdpu381-h264.c calls v4l2_h264_build_b_ref_lists().
This is a shared V4L2 helper correction, not a board-name-specific workaround.
No patch applied to the running kernel or in-progress AV1 build during audit.

Next priority: isolated A/B of this helper correction, keeping EBUSY and all
other variables constant; same pyramid/nonpyramid inputs, exact decoded frames,
then repeated browser runs and reference/buffer timing. It is a correctness
candidate, NOT established as the cause of ~260/1800 presentation drops.
Previous passing decoder hashes make that causal distinction particularly
important. A changed helper module needs matching build/signature and dependent
module unload checks; do not assume replacing rockchip-vdec alone changes it.
