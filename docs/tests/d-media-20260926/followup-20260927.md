# Optional D conversion throughput, 2026-09-27

Live ROCK 5B, kernel 6.18.50-vyos, HDMI input BGR 1920x1080 at 60 Hz.
Temporary native CLI configuration: GStreamer, negotiated colorimetry, 8000 kbps,
GOP 60. Local RTSP reader; no remote-network bottleneck in this comparison.

| Conversion | Frames actually decoded | Reader elapsed, including startup | Steady progress |
| --- | ---: | ---: | ---: |
| RGA v4l2convert, experimental_full_csc=Y | 600 | 10.964 s | about 60 fps |
| CPU videoconvert, experimental_full_csc=N | 120 | 17.447 s | about 10 fps |

Both readers exited successfully. FFmpeg used passthrough timestamps and a frame
limit, so its frame count is decoded output, not frames duplicated to meet a
nominal rate. Both streams declared limited-range BT.709 matrix and primaries;
the CPU path additionally declared sRGB transfer from its negotiated caps.
Publisher readiness must precede the reader. An eight-second ffprobe timeout
on the CPU path was insufficient for readiness/probing, not a service crash.

This is short throughput evidence, not a sustained stability, latency or pixel
accuracy test. It demonstrates a benefit over the GStreamer CPU conversion
fallback. The existing FFmpeg MPP path already achieved approximately 60 fps;
no superiority over that path is claimed. Defaults remain unchanged and the RGA
correction remains explicit opt-in on its validated hardware revision.

After testing, the parameter was restored to N, temporary D service configuration
removed and the original kiosk restored. Tailscale remained enabled throughout.
